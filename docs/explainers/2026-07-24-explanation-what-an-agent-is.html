1. A chat model answers; an agent loops

Start with the thing an agent is not. A chat model is a function: text in, text out. You ask a question, it writes an answer, and the interaction is over. Nothing happens in the world because of it.

An agent is that same model wrapped in a loop. The model is allowed to say, instead of an answer, "I need to do something first" — call a tool. The harness runs the tool, hands the result back to the model, and the model decides again: another action, or a final answer. Think, act, observe, repeat — until the model decides it is done.

Every other property people attach to the word "agent" — planning, memory, using files, delegating to other agents — is an elaboration of this loop. It is also why agents are risky in a way chatbots are not: a chatbot can only be wrong, an agent can be wrong with consequences. Everything in this repo's design follows from respecting that difference.

2. What makes an agent "deep"

The SDK this repo pins — LangChain's deepagents for TypeScript — ships a reference agent that is more than the bare loop. The extra machinery lives in middleware: layers that sit around the model call and around tool execution, intercepting what goes in and what comes out. Two properties of this stack matter for understanding the rest of the repo. First, middleware is replaceable by name: passing a middleware named FilesystemMiddleware into createDeepAgent swaps the default for yours — the mechanism this repo uses to give each agent its own tool allowlist. Second, the filesystem tools are only as safe as their backend: here every agent's backend is one shared directory in virtualMode, so .. and absolute-path escapes are rejected by the backend itself, not by anyone's good behavior.

3. Anatomy: one agent, as configured in this repo

Every agent in Agent Room is born in createRoomAgent, the factory that translates a plain config object into the SDK call. Stripped to its skeleton, this is what an agent is here:

const agent = createDeepAgent({
  model: config.model,          // a provider string, or a stub model in tests
  systemPrompt: config.systemPrompt, // the persona — identity AND chattiness policy
  tools: config.tools,          // extras beyond the built-ins (e.g. fetch_url)
  backend: config.backend,      // the shared, jailed workspace directory
  checkpointer,                 // SqliteSaver — one DB file per agent
  permissions: config.permissions,
  middleware,                   // tool allowlist + memory overrides
  name: config.name,
});

Each field is a load-bearing decision: the persona text carries the "speak up only when the topic is squarely yours" restraint; the tool allowlist never includes execute (no shell in v1); the checkpointer path is derived from the agent's id, so a relaunched app rebuilds the agent against its old memory.

Key concept An agent's identity (id, roster record, checkpoint file) is durable; its instance (the live object with middleware wired in) is disposable. Editing an agent stores new config and recreates the instance at the next turn boundary. Removing one deletes neither its messages nor its memory file.

4. A turn, end to end

What actually happens when you type @Scout why is the parser slow? and hit Enter. The numbered flow below is the real path through the code; the diagram carries a concrete example.

  1. The renderer sends one intent over IPC: postMessage(text). It knows nothing about agents.
  2. The broker appends the message to the room store (seq #12, say) and routes it: the @mention targets exactly one agent; everyone else just has it noted for later replay.
  3. The broker builds the agent's input — the room-context envelope: the roster (names + one-line personas) plus author-attributed messages, with anything the agent missed while busy marked as such. This is how Scout can tell you from Muse from itself.
  4. The turn runner invokes the agent's graph with streamMode: ["updates", "messages"] and subgraphs: true, and maps raw stream chunks onto a small event vocabulary: token, tool_call.start, tool_call.end, status, turn.end.
  5. Those events fan out to three independent projections: tokens are buffered into the reply text; the presence machine flips states; every event is appended to the store's event log, which the activity rail folds into tool cards.
  6. On turn.end(done), the reply becomes a room message — and if it @mentions another member, the chain continues, capped at depth 3 per user message.

5. Presence is a state machine, not a vibe

How does the UI know Scout is "running search_web…"? Not by watching tokens — an agent can work for a minute without emitting one. Presence is a small deterministic machine in the SessionManager, fed by the turn runner's structured events. The member list is a pure rendering of it:

connecting → idle → thinking → runningTool → thinking → idle
thinking / runningTool → error → idle (retry) · offline → connecting (manual retry)

Two invariants make this trustworthy. Transitions come only from events — tool_call.start moves an agent to runningTool and records the tool's name, which is exactly where the "running search_web…" line comes from. And the failure policy has no loops: one automatic recovery after a crash, then the agent goes offline and waits for a human to press Retry. Auth failures skip even that — a bad key never fixes itself.

6. Cancellation and time

Every turn carries an AbortController. Pressing Stop (or quitting the app) aborts it, and three things happen in order: the stream closes with turn.end(cancelled); any partial reply is kept in the room history with an interrupted marker; and the agent's delivery watermark stays put. That last one is the subtle part — the watermark tracks what the agent has been shown, so nothing is marked delivered, and the messages come back as input on its next invocation. The human's record stays truthful while the agent's view stays conservative. A turn that outlives a wall-clock timeout is treated as a hang and follows the crash path rather than reading as a clean cancel.

7. Memory: one truth, many recollections

The room store holds the verbatim record of everything — it is the single source of truth. Each agent's memory is a derived view of it, and it is allowed to differ. Three mechanisms compose that view:

  • Checkpoint. Each agent has a stable thread id and its own SQLite checkpoint file. A relaunched app rebuilds the agent against the same file, so the model wakes up with its working state intact.
  • Replay. A per-agent watermark in the store tracks what that agent has been delivered. Anything it missed — while busy, offline, or removed — is folded into its next invocation's input, marked as missed.
  • Summarization. Inside the checkpoint, the summarization middleware keeps recent messages verbatim and compresses older ones, so context stays bounded over a long room history.
Edge case worth knowing Because summarization is per-agent, two agents can honestly "remember" the same week differently. That is a feature of the design, not a bug: the room's verbatim record is the arbiter when it matters, and each agent's recall is just its working memory of it.

8. The boundaries an agent here cannot cross

The v1 posture is full autonomy within a constrained surface. There is no approval UI; the safety lives in what does not exist:

  • No shell. execute is never in the tool catalog, and validation rejects it. A Coder agent works through files and asks you in-room to run builds and tests — co-presence supplies the execution loop.
  • A jailed filesystem. Every file tool runs against one shared directory in virtual mode; traversal outside it is rejected by the backend, so the worst case is redo-able work in a sandbox.
  • Bounded conversation. Agent→agent mention chains cap at depth 3 per user message, self-mentions are dropped, and an agent's own messages never re-trigger it. The room caps at 8 agents.

The one-line summary of the whole design: the model proposes, the harness disposes, the store remembers, and the jail holds.
