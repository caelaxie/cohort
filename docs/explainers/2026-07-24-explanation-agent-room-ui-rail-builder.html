1. Background: the room beneath the glass

Agent Room is a desktop application with a simple conceit: one persistent chat room in which you and a small team of AI agents are co-present members. You can @mention an agent to direct work at it, agents may chime in unaddressed when a message is squarely in their domain, and each agent has its own long-term memory of the room's history. It is an Electron app, which means its architecture lives or dies by one fundamental boundary.

The Electron boundary, for newcomers

Every Electron app is really two programs stapled together. The main process is a Node.js process: it can read files, open databases, and hold long-lived state. The renderer is a Chromium browser window: it runs React, paints pixels, and is deliberately kept away from the filesystem and the network. Between them sits a narrow bridge: a preload script that exposes a hand-picked set of functions over Electron's IPC (inter-process communication) channels.

This boundary is not a nuisance to be worked around — it is the security model and the mental model. The rule this codebase follows is worth stating plainly, because almost every file in this diff is shaped by it:

Key concept The renderer is a pure view. It holds no source of truth, makes no routing decisions, and never touches the model APIs. It sends intents ("post this message", "cancel that turn", "create an agent") and renders whatever the main process pushes back.

The cast of characters in the main process

Four main-process objects matter for this story, and they were all built in earlier units (U1–U5):

Main process (Node)

SessionManager owns one createDeepAgent instance per agent — a LangChain "deep agent" (an LLM with tools, middleware, and memory). It runs a presence state machine per agent: connecting idle thinking runningTool error / offline. It also owns per-turn AbortController cancellation.
Broker decides who speaks when. It routes @mentions, runs the chime-in relevance gate for unaddressed messages, keeps a per-agent FIFO queue, and caps agent→agent chains at depth 3 so two agents can't talk themselves into a loop.
RoomStore a SQLite database that is the source of truth: every message, the agent roster, and — crucially for U7 — an append-only event log of raw turn events.
Turn runner executes one agent turn and maps the LangGraph stream onto a small room-event vocabulary: token, tool_call.start, tool_call.end, status, turn.end.

The main process as it stood after U5. All of it worked — but you could only drive it from tests.

Memory and the workspace

Two more pieces of context complete the picture. First, each agent's memory is a SQLite LangGraph checkpoint (one file per agent) plus a summarization middleware: recent messages stay verbatim, older history is summarized. Second, all agents share one workspace directory, jailed by the SDK's filesystem backend in virtualMode — path traversal is rejected at the backend, not by convention. There is deliberately no shell tool anywhere in the product.

2. Narrow background: what existed when this work began

After U5, the room was a brain without a face. Agents could be created in code, invoked through the broker, and they remembered things across restarts. But there was no window to look at, no way to make an agent without writing TypeScript, and when an agent went off to do work you had no idea what it was doing unless you read the raw event table by hand.

The plan assigned the face three units, which this diff delivers:

  • U6 — the room surface: conversation, member list with live presence, and a composer, all over a new IPC layer.
  • U7 — the activity rail: a per-agent "what is everyone doing" view that never requires reading scrollback.
  • U8 — the builder: create, edit, and remove agents in-app, with starter presets and a settings pane for API keys.

Plus two things the plan's verification contract demanded: an end-to-end smoke gate (npm run smoke) and the unglamorous work of making the whole thing actually launch (which, as we'll see in §5, was harder than it sounds).

3. Intuition: three ideas that carry the whole diff

If you take three ideas away from this change set, everything else is elaboration.

Idea 1: The renderer speaks in DTOs and events, never in objects

Because the renderer is a pure view, the entire relationship between the two processes can be written down as one TypeScript file: src/shared/room-types.ts. It declares the data the renderer is allowed to see (a RoomSnapshot of messages and members), the live events it may receive (RoomPushEvent), and the intents it may send (the RoomClient interface). The preload script implements that interface over IPC; in tests, a FakeClient implements it in-memory, so every React component is testable without Electron at all.

Notice the direction of fit. The renderer does not poll: it hydrates once from a snapshot, then applies a stream of small push events. This is the same shape as a database view kept current by a change feed — and it sets up the second idea.

Idea 2: The activity rail is a fold over an event log

The activity rail answers "what is Scout doing right now?" The naive design would have the UI watch token streams — but tokens are the wrong signal (an agent can think for a minute without emitting one). The right signal is the turn-event vocabulary the turn runner already emits. So the broker appends every raw turn event to the room store's event log, and a new main-process object — the ActivityProjector — folds that log into per-agent activity state.

"Fold" is the operative word. The projector is a pure function from sequence of events to current view:

Event log (SQLite, append-only)

41turn.begin{triggerSeqs: [12]}
42tool_call.startsearch_web {q: "parser perf"}
43token"Let me"
44tool_call.startwrite_file {file_path: "notes.md"}
45tool_call.endwrite_file ✓ 120ms
46tool_call.endsearch_web ✓ 380ms
47turn.end{reason: "done"}
⟶

Projected view (per agent)

done search_web 380ms
done write_file 120ms
producednotes.md
turn outcome: done · from msg #12

State = fold(events). Tokens are folded for liveness only — they never trigger a push to the renderer.

Because the log is persisted, the fold is reproducible. A reloaded renderer doesn't need a snapshot format of its own: it asks for the roster-complete snapshot (which carries a high-water mark — the highest event sequence number folded so far) and then simply ignores any live push whose eventSeq is at or below that mark. Catch-up without duplicates falls out of the design for free.

Why this is event sourcing in miniature The write side (broker appends) and the read side (projector folds) are separated by the log. The same events feed the token buffer that assembles the reply text, the presence machine, and now the rail — three independent projections of one truth. Adding a fourth view later costs a new fold function, not a new event protocol.

Idea 3: An agent is a replaceable instance behind a stable identity

U8 makes agents editable. The subtlety: a running agent is a live LLM instance with middleware and memory wired in, so you cannot mutate its persona mid-flight. The resolution is to treat the instance as disposable and the identity (id, roster record, checkpoint file) as durable:

  • Edit writes the new config to the store, then asks the SessionManager to reconfigure: the in-flight turn finishes on the old instance, and the next turn runs on a freshly created one. Name and avatar changes apply to future messages; old messages keep the name and avatar captured when they were written (which is why the messages table grew an avatar column in this diff).
  • Remove cancels any in-flight turn, writes an interruption marker and a system note, drops the agent from the roster — and leaves its messages and its checkpoint file on disk. History never rewrites attribution.
  • Relaunch calls restoreAgents(): every roster record is re-registered and started against its old checkpoint, so agents come back online with their memories intact.

Turn N (old config)

instance #1persona: "careful researcher"
thinking…user clicks Save mid-turn
⟶

Turn N+1 (new config)

instance #2persona: "terse fact-checker"
memory: {trigger: 5, keep: 2}
recreatedonly after turn N settled

reconfigure() defers the swap to the turn boundary. The room never sees a half-edited agent.

4. Code: a guided walkthrough

The diff is large, but it organizes into six layers that stack on top of each other. We'll go bottom-up, from the shared vocabulary to the pixels, then look at the lifecycle wiring and the smoke gate.

4.1 The shared vocabulary — src/shared/

room-types.ts gained the rail DTOs (ToolCallDto, TurnActivityDto, AgentActivityDto), the builder DTOs (AgentOptionsDto, SaveAgentResult), an avatar on both members and messages, and five new RoomClient methods for the agent lifecycle. A new pure module, agent-config.ts, holds the catalog both sides validate against:

The same module defines the three presets — Researcher, Coder, Writer — whose personas carry the product's chattiness policy as prose ("You speak up only when the topic is squarely yours… otherwise you stay silent"). That was a deliberate product decision: there is no chattiness slider, the personality lives in the persona text, and the relevance gate uses that very text as its judging rubric (verified by a test that captures what the gate receives).

4.2 Main process, part 1 — the projector and the store

The room store learned two new tricks: an avatar column on messages (with an ALTER TABLE migration for older databases, same pattern as the earlier interrupted column), and subscribeEvents — the event-log equivalent of the existing message subscription. The projector consumes both the historic log and the live feed through one code path:

constructor(options: ActivityProjectorOptions) {
  // 1. Fold everything that already happened…
  for (const record of this.store.listEvents()) {
    this.fold(record, false);
  }
  // 2. …then keep folding as new events land.
  this.unsubscribe = this.store.subscribeEvents((record) => {
    this.fold(record, true);
  });
}

The fold itself is a switch over event kinds. tool_call.start opens a card (nesting one level under the most recent open card when the event carries a subgraph namespace — that's how subagent steps attach to their parent). tool_call.end closes it and stamps the duration from event timestamps. write_file/edit_file starts contribute produced items, deduped by path. turn.end settles the turn, marking any still-open cards interrupted or errored depending on the outcome. Two details worth knowing:

  • Only turn-boundary and tool events notify listeners. Tokens and status events update a liveness timestamp silently — otherwise the renderer would receive one activity push per token, recreating the very thrash the streaming layer works to avoid.
  • DTOs are copied by value at the boundary (cards and children mapped), so a fold that happens after a push can never mutate the snapshot a listener already received.

4.3 Main process, part 2 — lifecycle surgery

The SessionManager gained the two operations the builder needs, each about twenty lines and each with a sharp edge case handled by the presence machine:

async stopAgent(agentId) {

And the RoomHost façade grew the orchestration the IPC layer calls: createAgent (validate → slug id → roster record → register → start), updateAgent (validate → persist → reconfigure), removeAgent (cancel → stop → delete → system note), restoreAgents (re-register and start every stored agent on relaunch), and getAgentOptions/getAgentConfig for the builder's form state.

The broker got smaller, sharper changes: it logs a turn.begin marker at dispatch (which chat messages spawned this work — that's how rail cards link back to the conversation), stamps avatars onto agent messages at write time, and generates turn ids with a per-boot prefix so ids never collide across app restarts.

4.4 The bridge — ipc.ts and preload/index.ts

Five new IPC channels (agents:get-options, agents:get-config, agents:create, agents:update, agents:remove) plus activity:get-snapshot. Every handler re-validates on the main side — the renderer's inline validation is a courtesy, never a boundary. The preload maps each channel onto the RoomClient interface one-to-one; there is no cleverness here, which is exactly the point of a security seam.

4.5 The renderer — room, rail, builder

The room UI (U6) renders from useRoomState: messages hydrate once, streaming tokens buffer per agent and flush once per animation frame, presence dots come from session events and never from token arrival. The composer has a @mention autocomplete, keeps drafts on failed sends, and stays disabled until at least one agent exists — the first-run empty state routes you into the builder instead.

The three panes and what drives them: member list ← presence machine; chat ← room store; rail ← projector fold.

The rail (U7) mirrors the projector's shape one-to-one: a section per agent, the live turn's cards with status chips and ticking durations, args/output truncated behind a toggle, subagent steps nested under their parent card, produced files listed in green, older turns collapsed behind an "earlier turns" disclosure, and an honest "idle — last active 5m ago" for quiet agents. A just-settled turn stays visible precisely so an interrupted chip is glanceable; only older turns fold away.

The builder (U8) is a controlled form over the shared catalog: name, an emoji-and-color avatar picker, persona textarea, model dropdown, tool checkboxes, and an optional memory-overrides section. Inline errors come from the same validateAgentConfig the main process re-runs on save. The settings pane is deliberately tiny: one password field for the Anthropic key, stored via Electron's safeStorage.

5. The two bugs found in review

Two defects surfaced during the final review pass. Both are instructive because they are boundary bugs — places where two of the architecture's seams rubbed.

Bug 1 — the turn that never ended The broker logs turn.begin at dispatch, and the projector settles turns on turn.end. But when the target agent is offline, sendTurn returns an error without ever running the turn runner — so no turn.end is ever emitted, and the rail showed that turn as "working…" forever. The fix is six lines: on an error outcome, the broker appends a synthetic turn.end itself. When the runner already emitted one, the extra fold is a no-op — the projector's settleTurn ignores events for a turn that has already closed.
Bug 2 — one binary, two incompatible runtimes better-sqlite3 is a native module, and native modules are compiled against a specific ABI. Electron 33 wants ABI 130; the system Node (which runs the tests) wants ABI 137. The original postinstall script was meant to rebuild it for Electron, but a misplaced -o flag had made it rebuild a pure-JS package instead — a silent no-op since the day it was written. The app crashed on launch; the tests were fine. The durable fix lives in package.json: predev rebuilds for Electron, pretest/presmoke rebuild for Node, and postinstall now uses the correct flags.

There's a moral in the second one. A verification step that can't fail loudly ("Rebuild Complete" printed whether or not anything was rebuilt) hid the problem until someone tried to run the app. The smoke gate now exercises the launch path — but only an actual launch caught the ABI mismatch, which is why the final summary called out "not verified by eye" as a residual risk until the app was run.

6. Quiz: did it stick?

Five questions, medium heat. Click an answer to check it.

1. Why does the ActivityProjector fold events from the SQLite log instead of subscribing directly to the SessionManager's event stream?

Right — the log is the projector's persistence. Hydrate from a snapshot stamped with a high-water mark, then drop live pushes at or below it: catch-up with no duplicates, and no second snapshot format to keep in sync.
Not quite. The key property is reproducibility: the same append-only log feeds every projection (reply assembly, presence, rail), so any consumer can refold from scratch and arrive at the same state.

2. You edit Scout's persona and click Save while Scout is mid-turn. What happens?

Correct — reconfigure stores the new config and sets pendingRecreate; when the turn settles, the instance is rebuilt and the queue is pumped. A half-edited agent never exists.
No — instances are treated as disposable. The edit waits for the turn boundary, then the agent is recreated from the stored config. History and the checkpoint file carry over; only the live instance is swapped.

3. A turn is cancelled mid-stream. What happens to the partial reply and the agent's delivery watermark?

Right. The room record stays truthful (the partial exists, marked interrupted), while the agent's derived view is conservative: nothing is marked delivered, so the messages come back as input next time the agent is invoked.
The watermark deliberately does not advance on cancellation. The partial reply is preserved for the human reader with an interrupted marker, but the agent will see the undelivered messages again on its next invocation.

4. The member list shows "running search_web…" under Scout's name. Where does that status line come from?

Exactly. Presence is a first-class state machine fed by structured events; the status line is derived from the latest tool call. Token arrival never changes presence — an agent can be mid-tool-call with zero tokens flowing.
Presence comes from the SessionManager's state machine, which consumes the turn runner's structured events (status, tool_call.start/end, turn.end). Deriving it from token traffic would freeze the UI exactly when the agent is doing something interesting.

5. Why does package.json now rebuild better-sqlite3 in both predev and pretest?

Right — ABI 130 (Electron 33) vs ABI 137 (system Node). The binary lives at one path, so the last rebuild wins. The hooks make each flow self-healing; the original bug was a flag that made the Electron rebuild a silent no-op.
It's an ABI conflict: a native module compiled for Electron can't load in system Node and vice versa. Since both share one file path, each entry point rebuilds for its own consumer.
